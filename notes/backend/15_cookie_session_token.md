# 쿠키, 세션, 토큰

## 쿠키, 세션, 토큰 요약
무상태인 HTTP에서 로그인 상태를 유지하는 방법으로 쿠키, 세션, 토큰(JWT)의 개념과 차이, Access/Refresh Token, 로그아웃 처리를 정리한 이론 레슨이다. 코드 실습은 없다.

## 인증(Authentication)과 인가(Authorization)의 차이
- 인증(Authentication): 사용자나 장치의 신원을 확인하는 과정이다. 로그인이 대표적인 인증 절차이다.
- 인가(Authorization): 요청한 작업을 수행할 권한이 있는지 확인해 허용하거나 거부하는 과정이다. 예를 들어 관리자는 공지사항을 쓸 수 있지만 일반 사용자는 못 쓴다.

강의의 비유로는 술집 입장이 있다. 신분증이 없으면 인증 실패, 고등학생 학생증으로 신원은 확인됐지만 나이 권한이 없으면 인가 실패, 성인 신분증이면 인증·인가 모두 통과해 들어간다.

## HTTP 무상태와 로그인 상태 유지 문제
HTTP는 무상태(Stateless) 프로토콜이다. 요청 하나하나가 독립적으로 처리되며, HTTP 자체는 이전 요청의 로그인 여부를 기억하지 않는다. 그런데도 로그인 후 페이지를 옮기거나 새로고침해도 로그인이 유지되는 이유가 쿠키, 세션, 토큰 같은 수단이다.

## 쿠키, 세션, 토큰, JWT의 역할 비교
- 쿠키: 브라우저가 데이터를 저장하고, 조건에 맞는 요청에 자동으로 실어 보내는 수단
- 세션: 서버에 사용자 상태를 저장하고, 전달받은 세션 ID로 조회하는 방식
- 토큰: 인증이나 접근 권한 확인 때 제시하는 값
- JWT: 사용자 식별자 등의 정보를 담을 수 있는 토큰 형식의 하나

쿠키는 저장·전송 수단일 뿐이라, 쿠키 안에 세션 ID를 담을 수도 있고 JWT를 담을 수도 있다.

## 쿠키(Cookie)란과 대표 속성
쿠키는 웹 브라우저에 저장되는 작은 데이터 조각이고, 브라우저가 조건에 맞는 요청에 자동으로 포함해 서버로 보낸다.
- `Expires` / `Max-Age`: 만료 시각 / 남은 유효 시간(초)을 정한다.
- `HttpOnly`: JavaScript에서 쿠키에 직접 접근하지 못하게 막는다.
- `Secure`: HTTPS 요청에만 쿠키를 보내도록 제한한다.

## 세션(Session) 기반 로그인 방식
세션은 여러 요청에 걸쳐 사용자 상태를 유지하는 방식이다.
- 사용자 식별자, 로그인 여부 같은 세션 정보는 서버 쪽 DB, 메모리, Redis 등에 저장한다.
- 클라이언트에는 세션 ID만 주고, 서버는 요청에 담긴 ID로 세션 정보를 찾는다.
- 브라우저에서는 보통 세션 ID를 쿠키에 저장한다.
- 서버가 세션을 지우거나 만료시켜 로그인 상태를 끊을 수 있다.

(강의의 흐름 그림은 이미지라 내용 확인 불가)

## 토큰(Token) 기반 인증 흐름
토큰은 인증이나 접근 권한 확인에 쓰는 값이다.
- 로그인에 성공하면 서버가 토큰을 발급하고 클라이언트가 저장한다.
- 인증이 필요한 요청에 저장한 토큰을 함께 보내면, 서버가 토큰을 검증해 사용자를 확인한다.

## JWT(JSON Web Token)란과 장점
JWT는 JSON 형태의 정보를 담아 전달하는 표준 토큰 형식으로, 주로 인증과 정보 교환에 쓴다. JWT도 쿠키에 넣어 요청에 실을 수 있다. 내용은 `https://www.jwt.io/`에서 디코딩해 볼 수 있다.
- 자가 수용성(Self-contained): 토큰 안에 사용자 식별자 등의 정보를 담는다.
- 확장성(Scalability): 서버가 세션 저장소를 조회하지 않고 토큰만으로 검증할 수 있어 서버를 여러 대로 늘릴 때 유리하다.

## JWT 구조: 헤더, 페이로드, 서명
일반적인 서명형 JWT는 세 부분으로 되어 있다.
- 헤더: 서명 알고리즘, 토큰 타입 등 메타데이터
- 페이로드: 사용자 식별자, 만료 시각 등의 정보(claim)
  - `sub`: 토큰의 주체. 사용자 인증에서는 사용자 ID 등
  - `exp`: 만료 시각
  - `iat`: 발급 시각
  - 페이로드는 Base64URL 인코딩일 뿐 암호화가 아니므로 비밀번호 같은 민감 정보를 넣으면 안 된다.
- 서명: 토큰 내용이 위변조됐는지 검증하는 데 쓴다. 내용은 누구나 읽을 수 있어도 서명 키 없이는 내용을 바꾼 뒤 유효한 서명을 만들 수 없다. 예를 들어 HS256은 서버의 비밀 키로 서명을 만들고 검증하며, 비밀 키는 토큰에 넣지 않는다.

## JWT 검증 원칙: 디코딩과 검증은 다르다
JWT 페이로드를 디코딩해서 읽는 것과 토큰을 검증하는 것은 다른 일이다.
- 서버가 허용한 알고리즘과 키로 서명을 검증한다.
- 인증용 토큰에는 만료 시각 등 필요한 claim을 넣고, 서버에서 그 claim이 있는지와 값이 맞는지 검증한다.
- 검증되지 않은 페이로드의 사용자 ID나 권한을 믿으면 안 된다.

## JWT 사용 시 주의할 점
- 일반적으로 세션 ID보다 크기가 크다.
- 한 번 발급한 토큰은 만료 전에 개별적으로 무효화하기 어렵다.
- 토큰에 담긴 권한만 보고 판단하면, 서버에서 사용자 권한을 바꿔도 이미 발급된 토큰에는 즉시 반영되지 않는다.

## Access Token과 Refresh Token
Access/Refresh는 토큰의 역할 구분이고, JWT는 토큰의 형식이다. 둘은 다른 축의 개념이다.
- Access Token: 인증이 필요한 API나 리소스에 접근할 때 쓴다. 탈취돼도 쓸 수 있는 시간을 줄이려고 유효기간을 비교적 짧게 둔다.
- Refresh Token: Access Token 재발급에 쓴다. 보통 Access Token보다 유효기간이 길고, 서버가 유효 여부를 확인하고 폐기할 수 있도록 DB 등에 관리하기도 한다.
- Refresh Token은 선택 사항이다.

## 세션 방식과 JWT 방식의 로그아웃과 만료 처리
- 세션 방식: 서버의 세션을 무효화하고, 브라우저의 세션 ID 쿠키도 삭제한다.
- JWT 방식: 클라이언트에 저장된 토큰을 지우고 이후 요청에 토큰을 보내지 않는다.
- Refresh Token을 폐기하면 그 토큰으로 하는 재발급은 막을 수 있다. 하지만 이미 발급된 Access Token까지 같이 무효화되지는 않는다.

## 쿠키, 세션, 토큰 복습 Q&A
- Q. 인증과 인가의 차이는?
  A. 인증은 누구인지 신원을 확인하는 것이고, 인가는 그 사용자가 요청한 작업을 할 권한이 있는지 확인하는 것이다.
- Q. 세션 방식에서 클라이언트(브라우저)에 저장되는 것은?
  A. 세션 ID만 저장되며 보통 쿠키에 담긴다. 세션 정보 자체는 서버(DB, 메모리, Redis 등)에 있다.
- Q. JWT 페이로드에 비밀번호를 넣으면 안 되는 이유는?
  A. 페이로드는 Base64URL 인코딩일 뿐 암호화되지 않아 누구나 읽을 수 있기 때문이다.
- Q. JWT의 sub, iat, exp claim은 각각 무엇인가?
  A. sub는 토큰 주체(사용자 ID 등), iat는 발급 시각, exp는 만료 시각이다.
- Q. Refresh Token을 폐기하면 기존 Access Token도 바로 못 쓰게 되나?
  A. 아니다. 재발급만 막을 뿐, 이미 발급된 Access Token은 만료될 때까지 유효하다.
